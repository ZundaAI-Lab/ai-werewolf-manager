# 1ゲーム通しテスト手順

## 1. 目的

添付ZIPのAI人狼マネージャーを使用し、ランダムな8人村を新規作成して、勝敗公開後の全参加者の感想登録を経て`ended`になるまで通しテストを実施してください。

各AIターンでは、アプリが生成した実際の`promptText`をAIが読み、生回答`rawResponse`を生成し、本番のパーサー・バリデーター・状態遷移へ順番に通してください。

定型応答、疑似応答、対象名の機械置換、筋書きによる進行は禁止します。

---

## 2. 実行方式

本手順の責務は、**本番ソースが生成するプロンプトの品質を1ゲーム通して評価すること**です。配布アプリの製造可否、Windows配布物の起動確認、bundle生成物の鮮度・整合性確認はリリース検証の責務であり、本通しテストの開始条件には含めません。

入力ZIPは**Python標準`zipfile`で展開**してください。LinuxのInfo-ZIP `unzip`は使用しません。日本語ディレクトリ名・ファイル名を含むパスをそのまま保持し、展開後に`docs/tests/1ゲーム通しテスト手順.md`と`app/renderer/data/`配下の日本語パスが正常に参照できることを確認します。

通しテストは、展開したプロジェクトの作業用コピーから最新の本番ES Modulesを直接呼び出す**ソースレベル通しテスト**として実行してください。作業用コピーにはNode実行に必要な最小限の環境適合だけを行い、本番ロジック、プロンプト、パーサー、バリデーター、状態遷移、データは変更しません。

ソースレベル試験で使用する正本は次です。

- 本番ES Modules: `app/renderer/js/`
- Renderer入口: `app/renderer/js/app/bootstrap.js`
- キャラクター等の本番データ: `app/renderer/data/`
- Electron Main・保存・API通信が必要な場合: `app/main/`
- ゲーム回帰・本番関数の参照: `tools/tests/game/`
- AIタスク登録ルーティングの正本: `app/renderer/js/ui/controllers/aiTaskCommitController.js`

AI回答は、このスレッドのAIが各`promptText`を一件ずつ独立入力として読み、対象キャラクターとして`rawResponse`を生成します。定型応答、疑似応答、対象名の機械置換、筋書きによる進行は禁止します。

勝敗公開後は、全参加者の`result-impression`を本番AIタスクとして順に処理し、全員分の登録完了後にのみゲームを`ended`へ進めてください。

実行経路は必ず次のとおりです。

```text
本番prepareAiTaskでpromptText生成
→ AIによるrawResponse生成
→ 本番evaluateAiTaskCandidateでパース・検証
→ aiTaskCommitControllerと同じタスク別登録経路で本番状態へ登録
→ 本番状態検証
→ 状態更新後に次タスク生成
```

各`promptText`は新しい独立入力としてAIへ渡してください。前ターンのプロンプト、回答、完全状態、テスト側の推理や正解情報を同じ入力コンテキストへ残してはいけません。再試行も、元の`promptText`と今回の検証エラーだけを渡す新しい独立入力として実行してください。

## 3. 開始前確認

開始前確認は、Prompt通しテストを開始できることと、途中で補助ランナーの未対応タスクへ止まらないことの確認だけを目的とします。**`npm ci`、`npm run verify`、正規ビルド、配布版起動、bundle再生成、Build ID・bundle SHA-256整合確認は実施しません。**

1. 元ZIPのSHA-256を記録する。
2. Python標準`zipfile`でZIPを展開する。Linuxの`unzip`は使用しない。
3. 展開後、次の正本からアプリバージョン、Schema、Prompt Specを確認する。
   - アプリ版: `app/package.json`と`app/renderer/js/config/constants.js`
   - Schema／Prompt Spec: `app/renderer/js/config/constants.js`
4. 次の通しテスト必須領域が存在し、読み取れることを確認する。

```text
app/package.json
app/renderer/js/
app/renderer/data/
tools/tests/game/
docs/tests/1ゲーム通しテスト手順.md
```

5. `app/renderer/js/services/aiTaskService.js`の`prepareAiTask`と`evaluateAiTaskCandidate`を本番経路として使用できることを確認する。
6. `app/renderer/js/ui/controllers/aiTaskCommitController.js`の`commitAiTaskCandidate`にある最新タスク分岐を確認し、補助ランナーが同じ登録先をすべて扱えることをゲーム開始前に確認する。
7. 特に`priority-answer`は通常発言へ流さず、`recordAiPriorityAnswer`へ`questionEventId: slotId`を渡す経路になっていることを確認する。
8. ゲーム初期化後、本番状態検証が成功することを確認してから1ターン目へ進む。

ZIP内の本番ソースは変更禁止です。作業用コピーへの環境適合調整は認めますが、本番ロジック、プロンプト、パーサー、バリデーター、状態遷移を変更してはいけません。

補助ランナーは進行と監査保存だけを担当し、ゲーム規則やAIタスクの意味を独自実装しません。AI回答、解析済み値、ゲーム状態を直接代入して継続してはいけません。

## 4. ゲーム設定

- 標準人狼
- 8人、全員AI操作
- キャラクター重複なし
- キャラクターはアプリのランダム選択
- 標準8人配役は村人×2、占い師、霊能者、狩人、狂人、人狼×2とし、役職対応はランダム
- 昼発言は1人3回、順番制、質問への回答優先あり。通常は3巡完了で昼議論完了とする。3巡目のCO後、そのCO時点で発言回数を使い切っていた生存者（CO者を除く）がいる場合だけ、対象者へCO再検討発言を1回ずつ追加する
- 初夜の人狼会話あり、初夜襲撃なし
- 初日占いは対象選択、初夜護衛なし
- 自己投票なし、棄権なし
- 投票中は非公開、確定後に全投票先を公開
- 決選投票上限は1回。上限後の同票はランダム処刑
- 処刑時の役職は非公開
- 人狼共有会話は人狼だけが参加し、各夜1人1回。襲撃がある夜は各生存人狼が秘密投票し、最多票の対象を襲撃する。最多同率は同率候補からランダム決定する
- その他は`app/renderer/js/config/constants.js`の`DEFAULT_RULES`に一致させる

乱数結果を都合よく変更してはいけません。シードを指定できる場合は保存し、できない場合はキャラクター、配役、発言順、初期設定をマニフェストへ保存してください。

---

## 5. AIターンの処理

各ターンを必ず一件ずつ、次の順序で処理してください。

1. 現在状態から本番`prepareAiTask(state, { playerId, taskType, slotId })`で対象プレイヤーの`promptText`を生成する。
2. `taskArtifact`の`promptText`、fingerprint、taskType、playerId、slotId、生成時public sequenceを監査データへ保存する。
3. AIはその`promptText`だけを新しい独立入力として読み、対象キャラクターとして`rawResponse`を生成する。
4. `rawResponse`を変更せず本番`evaluateAiTaskCandidate(state, taskArtifact, rawResponse)`へ渡し、本番パーサー・バリデーターの結果を得る。
5. 検証成功時だけ、`aiTaskCommitController.js`の`commitAiTaskCandidate`と同じタスク別登録経路で本番状態へ登録する。
6. 登録後に本番状態検証を行い、成功したことを確認する。
7. 状態更新後に次のAIタスクを取得し、同じ手順を繰り返す。

後続ターンの先行生成、複数ターンの一括生成は禁止します。

### タスク別登録経路

補助ランナーは、開始時点の最新`aiTaskCommitController.js`に合わせて少なくとも次を扱ってください。文字列の独自判定を増やさず、通常発言は`isNormalSpeechTask`、個人夜行動は`isPersonalNightAction`の本番判定を使用します。

| AIタスク | 本番登録先 | 必須の引き渡し |
| --- | --- | --- |
| `discussion-opening-preference` | `recordAiDiscussionOpeningPreference` | 検証済みopening preference |
| `result-impression` | `recordResultImpression` | `parsed.publicSpeech`ほか感想用項目 |
| `priority-answer` | `recordAiPriorityAnswer` | **`questionEventId: slotId`**、公開回答、CO・能力主張・判断更新 |
| `testament` | `recordAiTestament` | 公開遺言、CO・能力主張 |
| 通常発言タスク | `recordAiSpeech` | 公開発言、相互作用、CO・能力主張、判断更新 |
| `vote` | `recordVote` | `validation.resolvedAction.id` |
| 個人夜行動 | `recordNightAction` | `slotId`、actor、`validation.resolvedAction.id` |
| `wolf-attack` | `recordWolfAttackVote` | actor、`validation.resolvedAction.id` |
| `mason-conversation` | `recordMasonMessage` | 共有者会話本文 |
| `graveyard-conversation` | `recordGraveyardMessage` | 墓場会話本文 |
| `wolf-conversation` | `recordWolfMessage` | 人狼会話本文、共有戦略更新 |
| `memo-consolidate` | `consolidatePlayerInternalMemory` | `parsed.fullMemo` |

`priority-answer`は公開質問から発生する独立AIタスクです。質問元イベントIDを`slotId`のまま保持し、通常発言として代用しないでください。登録成功後に質問解決状態と次タスクを本番状態から取得します。

単一スレッドで実施した場合は、次を評価書へ記載してください。

- 単一AIによる逐次ロールプレイであること
- 独立した8エージェントを使用していないこと
- プロンプト本文の秘密情報混入は検査するが、モデル内部コンテキストの物理隔離を証明する試験ではないこと

### 参照可能な情報

AI判断に使用してよいのは、そのターンの`promptText`に含まれる情報だけです。次を混入させてはいけません。

- 他者の真役職、内部メモ
- 非公開の人狼仲間、能力結果、投票
- 将来の処刑、襲撃、勝敗
- テスト実行側の正解筋や完全状態の隠し情報

### 禁止する生成方法

- 名前、日付、候補、役職だけを置換するテンプレート
- ランダム選択だけで発言、投票、能力対象を決める処理
- 全員へ同じ文型を使用する処理
- 勝敗を先に決めて展開を合わせる処理
- AI回答を生成せず、直接イベントや状態を作る処理
- `parsed*`フィールドの手作業補完
- パーサーまたはバリデーターの迂回
- 失敗回答を削除して成功回答だけを残す処理

PythonやJavaScriptは、ZIP展開、進行、保存、ハッシュ、集計、検証、AI回答の受け渡しに使用できます。文章本文をテンプレートやルールベースで生成する用途には使用しないでください。

## 6. 応答と解析の検証

各`rawResponse`は、`promptText`が要求する単一JSONと必須キー・構造を満たさなければなりません。

解析済みフィールドは、保存済み`rawResponse`を本番パーサーで解析した結果だけを使用してください。

全ターンで次を確認してください。

```text
productionParser(rawResponse) == 保存されたparsed系フィールド
```

完全一致しない場合は不正ターンとして記録します。

### 検証失敗時

検証失敗はプロンプト品質の評価対象としてそのまま保存し、解析値やゲーム状態を手作業で直してはいけません。次の手順だけで再試行します。

1. 失敗した`rawResponse`、本番パーサー結果、本番バリデーターのエラー・警告を保存する。
2. 元の`promptText`と**今回の検証エラーだけ**を新しい独立入力としてAIへ渡し、`rawResponse`を再生成する。
3. 再生成した`rawResponse`を再び本番`evaluateAiTaskCandidate`へ渡す。
4. 検証成功した回答だけを本番タスク別登録経路へ渡す。
5. 初回失敗を含む全試行を監査データへ残し、成功回答だけに置き換えない。

再試行時も、テスト側から正解、候補の優先順位、非公開状態、具体的な修正文を追加してはいけません。検証エラーが「公開参照として無効」など具体的であっても、そのエラーメッセージ以上の誘導は行いません。

---

## 7. ゲーム判断

- 勝者、処刑者、襲撃者、COを事前に決めない。
- 投票先、能力対象、CO、潜伏、騙りは各AIの回答だけで決定する。
- 真占い師や真霊能者へCOを強制しない。
- 標準設定では自己投票を候補へ含めず、選択された場合は検証エラーとして扱う。
- 夜の占い、護衛、襲撃先投票は、AI応答JSONの`rationale`を本番パーサーで内部`selectionRationale`へ変換し、結果判明前に保存する。
- 選択理由には、その時点の具体的な発言、票、CO、能力結果、配役構造を含める。
- 人狼共有会話は実際に行い、前の人狼の発言を次の人狼のプロンプトへ反映する。
- GM判断が必要な停止状態では、展開を誘導しない中立的な判断を行い、操作と理由を記録する。

AIの発言類似、推理の浅さ、口調崩れ、不合理な判断、CO不足などは修正せず、プロンプト評価結果として保存してください。

COまたは能力結果公開がゲーム終了まで一件もなかった場合は、その機能を「未評価」と記載してください。

## 8. 無効・中止条件

### 無効条件

次のいずれかが発生した場合、AI判断・プロンプト評価用テストとして無効です。

- 必須JSONキー・構造を満たさない`rawResponse`を解析値で補完した
- `rawResponse`を通さず`parsed*`を作成した
- 本番パーサー、バリデーター、状態遷移を迂回した
- テンプレートまたは対象名置換で複数応答を作成した
- 前ターン確定前に後続応答を生成した
- 隠し情報をAI回答へ混入させた
- テスト実行側が展開を筋書きとして決定した
- 失敗回答を削除した
- 各ターンの`promptText`と`rawResponse`を監査できない
- 提出前の`ai_werewolf_8player_prompt_test_result.json`読込テストを実施していない、または失敗したファイルを提出した

無効になった場合は、理由と途中までの監査データを提出してください。

### 中止できる条件

次のいずれかに該当し、代替実行でも継続できない場合だけ中止できます。

- ZIPを読み取れない
- 通しテストに必要な本番ソースまたはデータがない
- 本番のプロンプト生成、解析、検証、状態遷移を特定または実行できない
- ソース破損によりゲームを初期化できない

ブラウザ、GUI、外部AI API、複数エージェント、ネットワーク、`npm install`、正規ビルドツールが利用できないことだけを理由に中止してはいけません。

## 9. 終了後の監査

最低限、次を機械集計してください。

### 応答経路

- AIターン数、タスク種別件数
- 必須見出し欠落、解析不一致
- パーサー・検証エラー、警告、API再試行、部分修復、再生成
- 項目単位・行単位の自動代替、GM上書き、本番経路迂回

### 発言・判断

- 公開発言数、キャラクター別発言数
- 一人称不一致、第三者視点、汎用発言
- 正規化後の完全一致文型と最多割合
- CO、能力結果公開、質問
- 投票変更、自己投票拒否件数、夜行動理由
- 結果判明前の選択理由保存率

### 記憶・安全性

- 通常タスクの`memoAdd`省略（既存メモ維持）・追記件数と、専用`memo-consolidate`タスクのAI応答`fullMemo`→内部`fullMemo`変換後の全文置換
- 秘密情報欠落・漏洩
- 人狼共有会話の村人プロンプト混入
- 直前の公開発言が次のプロンプトへ反映されなかった件数

問題がある場合は代表例を引用してください。

### 提出前の完全状態読込テスト

提出物をすべて生成した後、ZIP作成の直前に、提出予定の`ai_werewolf_8player_prompt_test_result.json`そのものを読み込んでください。

次をすべて満たすことを提出の必須条件とします。

1. メモリ上の状態ではなく、ディスクへ書き出した提出予定ファイルを改めて読み込む。
2. JSON構文解析だけで終えず、アプリ本番のインポート処理、状態正規化、Schema検証を通常の読込と同じ経路で実行する。
3. 読込前に未知項目の削除、値の補正、変換、サニタイズを行わない。
4. 今回の現行版が新規生成した提出JSON自体について、現行Schema・現行正規形・必須ゲーム事実の型・参照・状態不変条件に不一致が一件もなく、読込が成功することを確認する。本番インポートが版番号差を受理できることを理由に、提出JSON側の現行正規形検査を省略しない。
5. 読込後のアプリバージョン、Schema、終了Day、勝者、プレイヤー数、イベント数、AIターン数が、提出前の集計結果と一致することを確認する。
6. 読込テスト後に対象JSONを変更した場合は、変更後のファイルで最初から再実行する。
7. ZIPへ格納した同名ファイルのSHA-256が、読込テストに合格したファイルのSHA-256と一致することを確認する。

表示用タイムライン、評価書、集計データを生成するときは、完全状態のオブジェクトや`event.payload`を参照共有したまま加工してはいけません。表示用データはdeep copyして作成し、完全状態の生成前後ハッシュが一致することを確認してください。

読込テストに失敗した場合は提出してはいけません。成果物生成処理を修正し、完全状態JSONを再生成してから、読込テストとZIP内ハッシュ確認を再実行してください。本番インポートの「版番号ではなく現在必要な構造・型・参照で受け入れる」互換ポリシーをテスト都合で狭めたり、提出JSONをテスト側で補修して通したりしてはいけません。

マニフェストと評価書には、最低限次を記録してください。

- 読込対象ファイル名とSHA-256
- 使用した本番読込関数または実行経路
- JSON構文解析、状態正規化、Schema検証の各結果
- 読込後に照合した終了Day、勝者、プレイヤー数、イベント数、AIターン数
- ZIP内ファイルとのSHA-256一致結果
- 実施時刻

## 10. 提出物

次を提出してください。

1. `ai_werewolf_8player_prompt_test_result.json`  
   終了時の完全状態、全イベント、全AIターン、全プレイヤー状態、内部メモ、人狼共有会話、勝敗。

2. `ai_werewolf_8player_prompt_test_artifacts.json`  
   各ターンの`promptText`、`rawResponse`、パーサー結果、再解析結果、検証結果、失敗回答、状態前後ハッシュ、登録ID、生成方法。

3. `ai_werewolf_8player_prompt_test_timeline.json`  
   公開発言、CO、能力結果、投票結果、処刑、夜明け、勝敗の公開時系列。

4. `ai_werewolf_8player_prompt_test_manifest.json`  
   バージョン、Schema、Prompt Spec、入力ZIPハッシュ、実施時刻、乱数結果、配役、ルール、実施方式、試験対象、使用本番関数、補助スクリプト、環境適合調整、本番ソース変更有無、無効条件、完全状態JSONの本番読込テスト結果、読込対象SHA-256、ZIP内ファイルとのSHA-256一致結果。
