# 1ゲーム通しテスト手順

## 1. 目的

添付ZIPのAI人狼マネージャーを使用し、ランダムな8人村を新規作成して、勝敗公開後の全参加者の感想登録を経て`ended`になるまで通しテストを実施してください。

各AIターンでは、アプリが生成した実際の`promptText`をAIが読み、生回答`rawResponse`を生成し、本番のパーサー・バリデーター・状態遷移へ順番に通してください。

定型応答、疑似応答、対象名の機械置換、筋書きによる進行は禁止します。

---

## 2. 実行方式

次の優先順位で実行してください。

1. 正規ビルドした配布アプリで実行する。
2. 正規ビルドできない場合、最新の本番ES Modulesを補助スクリプトから直接呼び出す。
3. そのまま読み込めない場合、作業用コピーに限り、拡張子変更、import解決、ローダー設定、最小限のDOMスタブを使用する。

2または3で実施した場合は「ソースレベル通しテスト」と記録してください。Electronで生成された配布アプリを確認したとは扱いません。

現行構成では、正規配布アプリは`配布版を作成.cmd`または`tools`配下の`npm run release`が`output/dist/`へ生成するWindows x64版ZIP／Setup EXEです。配布アプリはElectron Mainの`app/main/`とRendererの`app/renderer/`で動作し、通常のWebブラウザへ`index.html`を直接開く方式ではありません。

ソースレベル試験で使用する正本は次です。

- 本番ES Modules: `app/renderer/js/`
- Renderer入口: `app/renderer/js/app/bootstrap.js`
- 配布bundle: `app/renderer/generated/bundle.js`
- Build ID: `app/renderer/generated/buildInfo.js`（`BUILD_ID`と`BUNDLE_SHA256`）
- Electron Main・保存・API通信: `app/main/`
- ゲーム回帰: `tools/tests/game/`
- デスクトップ回帰: `tools/tests/desktop/`

外部AI APIを使用できない場合は、このスレッドのAIが各`promptText`を一件ずつ読み、対象キャラクターとして`rawResponse`を生成してください。

勝敗公開後は、全参加者の`result-impression`を本番AIタスクとして順に処理し、全員分の登録完了後にのみゲームを`ended`へ進めてください。

実行経路は必ず次のとおりです。

```text
本番promptText生成
→ AIによるrawResponse生成
→ 本番パーサー
→ 本番バリデーター
→ 本番ゲーム状態遷移
```

各`promptText`は新しい独立入力としてAIへ渡してください。前ターンのプロンプト、回答、完全状態、テスト側の推理や正解情報を同じ入力コンテキストへ残してはいけません。再試行も、元の`promptText`と今回の検証エラーだけを渡す新しい独立入力として実行してください。

## 3. 開始前確認

### 完全ソースの判定

現行の完全ソースには、最低限次が必要です。

```text
AI人狼を起動.cmd
配布版を作成.cmd
ソース一式作成.cmd
README.md
app/README.txt
app/package.json
app/main/
app/renderer/
tools/package.json
tools/package-lock.json
tools/build/
tools/tests/
docs/
```

`ソース一式作成.cmd`が生成する`output/ai_werewolf_manager_vXX_XX_XX.zip`（製品版1.0.0では`output/ai_werewolf_manager_v01_00_00.zip`）は、`.github/`、`output/`、`tools/node_modules/`を意図的に除外します。この3領域がないことだけで差分ZIPまたは不完全ソースと判定してはいけません。反対に、`app/`、`tools/build/`、`tools/tests/`、`docs/`のいずれかが欠ける場合は完全ソースとして扱いません。

### 現行の検査・起動方法

Windowsで配布アプリを製造する場合は、プロジェクト直下の`配布版を作成.cmd`を使用します。成果物は`output/dist/`へ生成されます。ソース版をGUIで確認する場合は`AI人狼を起動.cmd`を使用します。

ソースだけを検査する場合は作業用コピーで次を実行します。

```text
cd tools
npm ci
npm run verify
```

`npm run verify`は、製造事前ゲート、決定的bundle生成、生成後の完全製造ゲート、ゲーム回帰、デスクトップ回帰の順で実行します。bundle生成により`app/renderer/generated/buildInfo.js`、`app/renderer/generated/bundle.js`、`app/renderer/index.html`のbundleキャッシュキーが更新されるため、元ZIPを不変のまま監査する場合は必ず作業用コピーで実施してください。

1. ZIPを展開し、次の正本からアプリバージョン、Schema、Prompt Spec、Build IDを確認する。
   - アプリ版: `app/package.json`と`app/renderer/js/config/constants.js`
   - Schema／Prompt Spec: `app/renderer/js/config/constants.js`
   - Build ID: `app/renderer/generated/buildInfo.js`（`BUILD_ID`と`BUNDLE_SHA256`）
2. 本アプリ固有のHTML、CSS、JavaScript、設定、データ、手順書が揃っているか確認する。
3. 差分ZIPしかなく、完全なベース一式が存在しない場合は中止する。
4. 利用可能な範囲で既存テストと正規ビルドを実行し、結果を記録する。
5. 宣言Build ID・BUNDLE_SHA256・現行ソース・同梱bundleの整合を確認する。
6. 不整合または正規ビルド不可の場合は、配布アプリ試験を未合格とし、最新ソースによるソースレベル通しテストへ切り替える。

`tools/node_modules`、`output`、`.github`、Webブラウザ、一般公開パッケージが同梱されていないことだけで差分ZIPと判定してはいけません。

ZIP内の本番ソースは変更禁止です。作業用コピーへの環境適合調整は認めますが、本番ロジック、プロンプト、パーサー、バリデーター、状態遷移を変更してはいけません。

補助スクリプトは作成可能ですが、本番処理を迂回してはいけません。

## 4. ゲーム設定

- 標準人狼
- 8人、全員AI操作
- キャラクター重複なし
- キャラクターはアプリのランダム選択
- 標準8人配役は村人×2、占い師、霊能者、狩人、狂人、人狼×2とし、役職対応はランダム
- 昼発言は1人3回、順番制、質問への回答優先あり。通常は3巡完了で昼議論完了とする。3巡目のCO後、そのCO時点で発言回数を使い切っていた生存者（CO者を除く）がいる場合だけ、対象者へCO再検討発言を1回ずつ追加する
- 初夜の人狼会話あり、初夜襲撃なし
- 初日占いは対象選択、初夜護衛なし
- 自己投票なし、棄権なし
- 投票中は非公開、確定後に全投票先を公開
- 決選投票上限は1回。上限後の同票はランダム処刑
- 処刑時の役職は非公開
- 人狼共有会話は人狼だけが参加し、各夜1人1回。襲撃がある夜は各生存人狼が秘密投票し、最多票の対象を襲撃する。最多同率は同率候補からランダム決定する
- その他は`app/renderer/js/config/constants.js`の`DEFAULT_RULES`に一致させる

乱数結果を都合よく変更してはいけません。シードを指定できる場合は保存し、できない場合はキャラクター、配役、発言順、初期設定をマニフェストへ保存してください。

---

## 5. AIターンの処理

各ターンを必ず一件ずつ、次の順序で処理してください。

1. 現在状態から本番コードで対象プレイヤーの`promptText`を生成する。
2. AIはその`promptText`を読み、対象キャラクターとして`rawResponse`を新規生成する。
3. `rawResponse`を変更せず本番パーサーへ渡す。
4. パーサー結果を本番バリデーターへ渡す。
5. 検証成功時だけ本番ゲームエンジンへ登録する。
6. 状態更新後に次のターンを生成する。

後続ターンの先行生成、複数ターンの一括生成は禁止します。

単一スレッドで実施した場合は、次を評価書へ記載してください。

- 単一AIによる逐次ロールプレイであること
- 独立した8エージェントを使用していないこと
- プロンプト本文の秘密情報混入は検査するが、モデル内部コンテキストの物理隔離を証明する試験ではないこと

### 参照可能な情報

AI判断に使用してよいのは、そのターンの`promptText`に含まれる情報だけです。次を混入させてはいけません。

- 他者の真役職、内部メモ
- 非公開の人狼仲間、能力結果、投票
- 将来の処刑、襲撃、勝敗
- テスト実行側の正解筋や完全状態の隠し情報

### 禁止する生成方法

- 名前、日付、候補、役職だけを置換するテンプレート
- ランダム選択だけで発言、投票、能力対象を決める処理
- 全員へ同じ文型を使用する処理
- 勝敗を先に決めて展開を合わせる処理
- AI回答を生成せず、直接イベントや状態を作る処理
- `parsed*`フィールドの手作業補完
- パーサーまたはバリデーターの迂回
- 失敗回答を削除して成功回答だけを残す処理

PythonやJavaScriptは、進行、保存、ハッシュ、集計、検証、AI回答の受け渡しに使用できます。文章本文をテンプレートやルールベースで生成する用途には使用しないでください。

## 6. 応答と解析の検証

各`rawResponse`は、`promptText`が要求する単一JSONと必須キー・構造を満たさなければなりません。

解析済みフィールドは、保存済み`rawResponse`を本番パーサーで解析した結果だけを使用してください。

全ターンで次を確認してください。

```text
productionParser(rawResponse) == 保存されたparsed系フィールド
```

完全一致しない場合は不正ターンとして記録します。

### 検証失敗時

最初の回答が失敗した場合は、次を保存してください。

- 最初の`rawResponse`
- パーサー結果
- エラーと警告
- 再試行用フィードバック

本番の`responseRecoveryMode`に従って処理してください。標準設定`repair-regenerate`では、直接生成または構造草案の候補取得で、応答修復とAPI再試行が共通基準予算4回を使用し、通常生成、失敗JSONの部分修復、元契約を維持した再生成を順に試します。多段生成では追加の必須工程分が計画予算へ加算され、校正は適用時に最大1回追加されます。状態不一致は回答修復せず最新プロンプトを一度再生成し、再試行可能なAPIエラーは適用される予算内で1回だけ再送します。各試行の`rawResponse`、解析、検証、工程、使用量を削除せず保存してください。

有効候補を取得できなかった場合は、本番`commitAiTaskFallback`を実行します。必須`actionAnswer`は、投票では本人の有効な投票予定、処刑候補、現行候補からのランダム選択の順で確定し、その他の対象選択では現行候補からランダム選択します。人狼・共有者会話は`なし`、通常発言は自動フォールバック、回答優先・勝敗後感想・内部メモ整理はスキップとして監査記録を残します。API本文を一度も取得できない失敗、公開／私有境界違反、代替登録失敗など本番が停止を要求する場合だけ「AI自動実行失敗」として終了してください。自動代替はゲーム継続には使用しますが、正常なAI回答としてプロンプト品質を加点しません。

## 7. ゲーム判断

- 勝者、処刑者、襲撃者、COを事前に決めない。
- 投票先、能力対象、CO、潜伏、騙りは各AIの回答だけで決定する。
- 真占い師や真霊能者へCOを強制しない。
- 標準設定では自己投票を候補へ含めず、選択された場合は検証エラーとして扱う。
- 夜の占い、護衛、襲撃先投票は、結果判明前に`actionRationale`を保存する。
- 選択理由には、その時点の具体的な発言、票、CO、能力結果、配役構造を含める。
- 人狼共有会話は実際に行い、前の人狼の発言を次の人狼のプロンプトへ反映する。
- GM判断が必要な停止状態では、展開を誘導しない中立的な判断を行い、操作と理由を記録する。

AIの発言類似、推理の浅さ、口調崩れ、不合理な判断、CO不足などは修正せず、プロンプト評価結果として保存してください。

COまたは能力結果公開がゲーム終了まで一件もなかった場合は、その機能を「未評価」と記載してください。

## 8. 無効・中止条件

### 無効条件

次のいずれかが発生した場合、AI判断・プロンプト評価用テストとして無効です。

- 必須JSONキー・構造を満たさない`rawResponse`を解析値で補完した
- `rawResponse`を通さず`parsed*`を作成した
- 本番パーサー、バリデーター、状態遷移を迂回した
- テンプレートまたは対象名置換で複数応答を作成した
- 前ターン確定前に後続応答を生成した
- 隠し情報をAI回答へ混入させた
- テスト実行側が展開を筋書きとして決定した
- 失敗回答を削除した
- 各ターンの`promptText`と`rawResponse`を監査できない
- 提出前の`ai_werewolf_8player_prompt_test_result.json`読込テストを実施していない、または失敗したファイルを提出した

無効になった場合は、理由と途中までの監査データを提出してください。

### 中止できる条件

次のいずれかに該当し、代替実行でも継続できない場合だけ中止できます。

- ZIPを読み取れない
- 完全なベースソースがない
- 本番のプロンプト生成、解析、検証、状態遷移を特定または実行できない
- ソース破損によりゲームを初期化できない

ブラウザ、GUI、外部AI API、複数エージェント、ネットワーク、`npm install`、正規ビルドツールが利用できないことだけを理由に中止してはいけません。

## 9. 終了後の監査

最低限、次を機械集計してください。

### 応答経路

- AIターン数、タスク種別件数
- 必須見出し欠落、解析不一致
- パーサー・検証エラー、警告、API再試行、部分修復、再生成
- 項目単位・行単位の自動代替、GM上書き、本番経路迂回

### 発言・判断

- 公開発言数、キャラクター別発言数
- 一人称不一致、第三者視点、汎用発言
- 正規化後の完全一致文型と最多割合
- CO、能力結果公開、質問
- 投票変更、自己投票拒否件数、夜行動理由
- 結果判明前の選択理由保存率

### 記憶・安全性

- 通常タスクの`memoAdd`省略（既存メモ維持）・追記件数と、専用`memo-consolidate`タスクの`consolidatedMemo`全文置換
- 秘密情報欠落・漏洩
- 人狼共有会話の村人プロンプト混入
- 直前の公開発言が次のプロンプトへ反映されなかった件数

問題がある場合は代表例を引用してください。

### 提出前の完全状態読込テスト

提出物をすべて生成した後、ZIP作成の直前に、提出予定の`ai_werewolf_8player_prompt_test_result.json`そのものを読み込んでください。

次をすべて満たすことを提出の必須条件とします。

1. メモリ上の状態ではなく、ディスクへ書き出した提出予定ファイルを改めて読み込む。
2. JSON構文解析だけで終えず、アプリ本番のインポート処理、状態正規化、Schema検証を通常の読込と同じ経路で実行する。
3. 読込前に未知項目の削除、値の補正、変換、サニタイズを行わない。
4. 今回の現行版が新規生成した提出JSON自体について、現行Schema・現行正規形・必須ゲーム事実の型・参照・状態不変条件に不一致が一件もなく、読込が成功することを確認する。本番インポートが版番号差を受理できることを理由に、提出JSON側の現行正規形検査を省略しない。
5. 読込後のアプリバージョン、Schema、終了Day、勝者、プレイヤー数、イベント数、AIターン数が、提出前の集計結果と一致することを確認する。
6. 読込テスト後に対象JSONを変更した場合は、変更後のファイルで最初から再実行する。
7. ZIPへ格納した同名ファイルのSHA-256が、読込テストに合格したファイルのSHA-256と一致することを確認する。

表示用タイムライン、評価書、集計データを生成するときは、完全状態のオブジェクトや`event.payload`を参照共有したまま加工してはいけません。表示用データはdeep copyして作成し、完全状態の生成前後ハッシュが一致することを確認してください。

読込テストに失敗した場合は提出してはいけません。成果物生成処理を修正し、完全状態JSONを再生成してから、読込テストとZIP内ハッシュ確認を再実行してください。本番インポートの「版番号ではなく現在必要な構造・型・参照で受け入れる」互換ポリシーをテスト都合で狭めたり、提出JSONをテスト側で補修して通したりしてはいけません。

マニフェストと評価書には、最低限次を記録してください。

- 読込対象ファイル名とSHA-256
- 使用した本番読込関数または実行経路
- JSON構文解析、状態正規化、Schema検証の各結果
- 読込後に照合した終了Day、勝者、プレイヤー数、イベント数、AIターン数
- ZIP内ファイルとのSHA-256一致結果
- 実施時刻

## 11. 最終回答

次を簡潔に記載してください。

- 有効／無効
- 配布アプリ試験／ソースレベル試験
- 正規ビルドとbundle整合結果
- 勝者、終了Day、AIターン数
- 検証エラー、解析不一致、秘密情報漏洩
