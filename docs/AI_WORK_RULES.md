# AI作業・製造規約

このファイルはコード変更とビルドの前に最初に参照する。`tools/build/manufacturingGate.js`は本規約の存在、現行ディレクトリ構成、必須実行モジュール、主要テスト入口、公開／私有情報境界、配布対象を検査し、違反時はテストおよびbundle生成を停止する。

1. ユーザーが明示していない既存機能を削除してはならない。
2. 「整理」「最適化」「簡素化」「重複排除」を機能削除の根拠にしてはならない。
3. ユーザー依頼に含まれない任意の改善は実装せず、必要に応じて提案として報告する。
4. 「共有停止」と「生成停止」を区別する。
5. 「公開しない」と「保存しない」を区別する。
6. 公開発言、心の声、内部メモ、判断状態、陣営戦略は別責務として扱う。
7. **絶対禁止: heartVoice機能、状態、履歴、保存、GM監査表示を削除してはならない。** heartVoiceは会話処理に使用しなくても演出上の必須機能である。AI応答での生成対象は昼議論（通常発言・回答優先発言）に限定するが、この出力範囲の限定をheartVoice機能そのものの削除、保存停止、履歴削除、表示削除の根拠にしてはならない。
8. heartVoiceは検証上の必須キーにせず、欠落だけをバリデーションエラーまたは再試行理由にしてはならない。ただし昼議論の生成指示・JSON例からは**絶対に削除してはならない**。昼議論以外の出力契約から外す変更は、heartVoiceの機能・状態・履歴・保存・監査表示を消す許可ではない。
9. 自由文解析の禁止を理由に、自由文表現機能そのものを削除してはならない。
10. モジュールの一部が不要でも、モジュール全体を削除してはならない。
11. 既存テストを削除して機能退行を隠してはならない。ユーザーがテスト追加・更新を明示していない場合、新規テスト追加と既存テスト変更を行わない。テスト結果は指定変更の確認材料であり、仕様を恒久的に保護する根拠として強調しない。ユーザーがテスト整理を明示した場合は、現行機能を直接守る高価値テストを残し、過去不具合専用・重複・実装詳細固定のテストを削除する。
12. モジュール責務または更新ルールを変更する場合は、対象ソース先頭のコメントも同時に更新する。

13. 任意とは回答検証上の必須条件ではないことを意味し、AIへその項目を見せるかどうかは別のプロンプト掲載契約で決める。特に`decisionPatch`の子項目は、機械的に受理可能な全項目を毎回見せず、今回の推理モード・人物傾向・処刑判断局面に応じてJSON例へ掲載する項目だけを選ぶ。
14. JSON例には、そのタスク・役職・局面で**今回AIに回答候補として見せる項目**を掲載する。CO・能力結果だけは無操作を主例へ置かず、必要時だけ使用する条件付き形式として別掲する。`decisionPatch`以外の固定掲載項目と、`heartVoice`など個別に掲載固定された項目は各契約を維持する。`decisionPatch`の許可キー一覧と今回の掲載キー一覧を同一集合として扱ってはならない。
15. 任意項目の未入力だけを理由として回答拒否、修復要求、再生成要求を行わない。JSON例へ掲載した任意項目はLLMに回答候補として考慮させるが、未入力だけを理由として警告昇格、登録停止も行わない。回答修復・再生成時も、そのターンで解決済みの掲載項目構成を維持し、非掲載の任意項目を勝手に追加したり、必須項目だけの最小形式へ縮退させたりしない。

## プロンプト掲載義務と回答検証義務の絶対分離

この節は、AI向けプロンプトへ項目を掲載する責務と、AI回答の欠落をエラーにする責務を混同しないための固定規約である。両者は独立した二つの真偽値として扱い、一方から他方を推定してはならない。

- **プロンプト掲載対象**: そのターンでAIに存在・用途・出力形式を認識させ、回答候補として考慮させる項目を意味する。固定掲載と動的掲載があり、動的掲載は局面・推理モード・人物傾向などの正本ポリシーから解決する。
- **回答検証必須**: AI回答にその項目が存在しない場合に、回答拒否・修復・再生成・登録停止の対象とすることを意味する。
- **任意項目**: 回答検証必須ではない項目を意味する。JSON例へ掲載されていても未入力を正常回答として無条件に受理し、欠落だけを理由に回答拒否、修復、再生成、警告昇格、登録停止を行ってはならない。
- **重要**: `プロンプト掲載必須=true`と`回答検証必須=false`は矛盾せず、正規の組み合わせである。ここで`プロンプト掲載必須`は、そのターンの掲載ポリシーで掲載対象に解決された項目についての意味であり、全許可項目を毎回掲載する意味ではない。また、`decisionPatch`では`機械許可=true`かつ`今回のプロンプト掲載対象=false`も正規であり、非掲載項目をAIへ回答要求しているものと解釈してはならない。

### ユーザー指示の解釈規則

次の表現は、ユーザーが同時に欠落時のエラー化を明示しない限り、**プロンプト掲載だけを要求する**ものとして扱う。

- 「プロンプトに明記する」
- 「JSON例に載せる」
- 「AIに出すように指示する」
- 「回答フェーズでも出す」
- 「生成対象にする」
- 「AIが判断できるよう情報を与える」

これらの表現を根拠に、`requiredTopLevelKeys`、必須Schema、欠落バリデーション、再生成条件へ項目を追加してはならない。回答検証必須へ変更できるのは、ユーザーが「未入力をエラーにする」「回答に必須とする」「欠落時は再生成する」など、欠落時の処理を明示した場合だけとする。

ユーザーが「任意」と指定した項目は、同時に「プロンプトへ必ず明記」と指定されても、回答検証上は必ず任意のまま維持する。後から「出すように」と指示されても、以前または同時に指定された任意性を上書きしてはならない。

### 実装上の責務境界

- `responseContract.js`はAI応答JSONの機械許可キーと回答検証必須キーの正本であり、`decisionPatch`で受理可能な全子項目もここに定義する。
- `decisionPromptFieldPolicy.js`は、受理可能な`decisionPatch`子項目のうち**今回JSON例へ見せる項目**を選ぶ唯一の正本である。ここでの掲載選択は回答必須性や永続保存対象を変更しない。
- `activeResponseContract.js`は、上記ポリシーで解決した今回の掲載集合を実際の説明・JSON例へ描画する**プロンプト掲載契約**である。
- `responseContract.js`の`requiredTopLevelKeys`は、欠落時に失敗させる項目だけを定義する**回答検証契約**である。
- プロンプト掲載契約を回答検証契約から自動生成してはならない。回答検証契約をプロンプト掲載契約から自動生成してはならない。
- 「プロンプトに必ず掲載する」という要件を実装するために、`requiredTopLevelKeys`へ追加することを絶対に禁止する。固定掲載・動的掲載のどちらでも、この禁止を維持する。反対に、`decisionPatch`の子項目が今回JSON例へ非掲載であることを理由に、パーサー許可キーから削除してはならない。
- 固定掲載契約を持つ項目は「任意だから」という理由でプロンプト指示・JSON例から削除しない。動的掲載契約を持つ`decisionPatch`子項目は、今回の掲載ポリシーに従って表示・非表示を決める。パーサー許可、既存の保存処理、履歴、GM監査表示の削除根拠にしてはならない。

### decisionPatchの動的掲載契約

`decisionPatch`のJSON例は、全AIへ同じ思考チェックリストを与えないため、許可された全子項目を毎回掲載しない。掲載された子項目はすべて回答任意であり、使用しなくてもエラーにしない。非掲載の子項目も機械許可契約から自動削除しない。

常時掲載する基本項目は次の4項目とする。

- `suspects`: 現在疑っている人物。
- `assessmentLevel`: 現在判断の強さ。
- `reason`: 現在判断を支える理由。
- `evidenceRefs`: 判断根拠となる公開ログ参照。

推理モードによる追加掲載は`decisionPromptFieldPolicy.js`の`MODE_FIELDS`を正本とする。

| 推理モード | 追加掲載する子項目 |
|---|---|
| `probe-response` | `unresolvedPoint`, `nextDiscriminatingInformation` |
| `evaluate-response` | `responseImpact`, `uncertainty` |
| `trace-change` | `changePoint`, `changeTrigger`, `changeNaturalness` |
| `check-consistency` | `conflictPoint`, `compatibleExplanation` |
| `inspect-commitment` | `commitmentAlignment`, `reversalExplanation` |
| `compare-pair` | `interactionAsymmetry`, `candidateDifference` |
| `challenge-consensus` | `consensusIndependence`, `counterHypothesis` |
| `evaluate-information-gain` | `nextDiscriminatingInformation` |
| `compare-candidates` | `comparisonAxis`, `candidateDifference` |
| `synthesize-claims` | `supportingSignals`, `counterSignals` |
| `hold-judgment` | `uncertainty`, `remainingHypotheses`, `nextDiscriminatingInformation` |

人物の推理傾向による追加掲載も同モジュールを正本とする。

| 条件 | 追加掲載する子項目 |
|---|---|
| `hypothesisBreadth=wide` | `remainingHypotheses` |
| `uncertaintyStyle=explicit` | `uncertainty` |
| `uncertaintyStyle=analytical` | `remainingHypotheses`, `nextDiscriminatingInformation` |
| `updateTempo=conservative` | `counterSignals` |
| `updateTempo=rapid` | `responseImpact` |

処刑比較項目の掲載タイミングは独自判定を作らず、`promptSituation.js`と`promptSectionPolicy.js`で解決済みの既存処刑判断フラグに一致させる。`showExecutionValuePolicy`が真、すなわち**実投票タスク**、または**順番制昼議論で本人の残り通常発言が1回以下となった通常発言／回答優先発言**で、`executionCandidates`, `leaveAliveBenefit`, `misexecutionCost`, `selectionDifference`を追加掲載する。`priority-answer`は通常発言回数を消費しないため、最終通常発言の前後どちらに割り込んでも同じ処刑判断局面として扱う。

`intendedVote`は実投票では掲載せず、上記の**最終昼議論判断局面だけ**追加掲載する。実投票先の正式な回答はトップレベル`actionAnswer`を使用する。

`correctedSpeechRefs`は、そのターンの例示参照として訂正対象の自分の公開発言番号が存在する場合だけ追加掲載する。

`confrontationStyle`と`questionStyle`は公開表現・質問方法の責務であり、それだけを理由に`decisionPatch`子項目を追加しない。推理モード固有の新規子項目は今回ターンの思考整理用であり、掲載されたことだけを理由に継続判断状態へ永続保存してはならない。

### heartVoiceの固定契約

昼議論の通常発言・回答優先発言における`heartVoice`は、次の契約を永久に同時成立させる。

| 契約軸 | 固定値 |
|---|---|
| プロンプトの項目説明 | 必ず掲載する |
| フェーズJSON例 | 必ず掲載する |
| パーサーでの受理 | 許可する |
| 入力された場合の保存 | 必ず保存する |
| 回答への入力 | 任意 |
| 未入力時のバリデーションエラー | 禁止 |
| 未入力だけを理由とする自動修復 | 禁止 |
| 未入力だけを理由とする再生成 | 禁止 |
| 未入力だけを理由とする登録停止 | 禁止 |

この固定契約の目的は、プロンプトへ書かなければAIが生成候補として認識しない一方、演出用の任意項目の欠落に再生成コストを費やさないことである。生成機会は確保するが、生成を強制しない。

### 必須回帰条件

通常発言と回答優先発言の両方で、次を同時に満たさなければ製造合格としてはならない。

1. 生成プロンプトとJSON例に`heartVoice`が存在する。
2. `heartVoice`を含む正常回答を解析・保存できる。
3. `heartVoice`を含まない正常回答も、修復・再生成なしで解析・検証・登録できる。
4. `heartVoice`欠落だけでは、エラー、警告昇格、自動修復、再生成、登録停止が一件も発生しない。
5. 多段生成、回答修復、再生成でも同じ任意性を維持する。

## プロンプト仕様の確認・評価・報告規約

1. プロンプトの問題を評価する前に、静的な完全契約やJSON例だけでなく、対象タスクから実際に生成される実行プロンプト、応答パーサー、意味検証、保存条件まで同じ経路で確認する。完全契約、フェーズ掲載契約、回答検証契約を相互に推定してはならない。
2. 実行プロンプトでAIに出力させる列挙項目は、その項目が掲載される同じフェーズ説明内へ許可値をすべて明記する。JSON例に代表値が一つあるだけでは列挙値の説明を満たさない。列挙値はドメインまたは機械契約の正本から取得し、プロンプト専用の別定義を作らない。
3. 任意項目がJSON例へ掲載され、未入力の回答も受理されることは正規仕様である。さらに`decisionPatch`では、機械許可された任意子項目が今回のJSON例へ非掲載になることも正規仕様である。これらを必須契約の不一致、検証不足、修正対象として報告してはならない。欠落時の失敗が正式要件として明示されている場合だけ、回答検証必須への変更を検討する。
4. 公開履歴の量を評価する前に、送信設定の`full` / `compact` / `delta`と、タスク・カーソル状態から解決される`full` / `compact` / `delta` / `night` / `night-delta` / `none`、参加者別カーソル、正常登録時だけのカーソル更新、再同期を確認する。`compact`は境界以前の構造化発言・判断根拠・各参加者の直近発言を保持し、境界後を全文で維持する。`full`モードの最大文字数だけを根拠に履歴削減を提案してはならない。履歴欠落、重複、カーソル誤更新などの実害を再現できた場合だけ不具合として扱う。
5. 問題一覧へ「最優先」「高」「重大」などの優先度表記を機械的に付けない。ユーザーが優先度付けを求めた場合、または進行停止、データ破損、秘密漏洩、正しい回答の恒常的拒否など明確な影響がある場合だけ、根拠を併記して使用する。通常の説明不足や改善事項は、対象と再現事実を簡潔に記載する。
6. 修正提案には、対象タスク、履歴モード、実際のプロンプト、AI原文、解析結果、検証結果、保存結果、違反する正式仕様を示す。正式仕様違反を示せない内容は不具合と断定せず、現行仕様を維持する。
7. Prompt Envelopeは`commonGameContext → taskInvariantContext → stablePlayerContext → taskVariableContext → dynamicTaskPrompt`の順を正本とする。キャッシュ対象は最初の3区画だけとし、役職・局面・会話段階・その回の出力契約など可変情報をキャッシュ効率のために前方へ移してはならない。`taskInvariantContext`には同一taskTypeで不変の意味ルールだけを置く。キャッシュ対象かどうかとProviderのsystem/user配置は別に扱い、Envelope再区分だけを理由に従来system側だった指示をuser側へ降格させてはならない。`dynamicTaskPrompt`はuser側の最終タスクとして末尾を維持する。
8. `dynamicTaskPrompt`および多段生成の各工程にある`## 最終確認`以下は、軽量LLMにも今回最低限必要な返却条件を応答直前に提示する固定末尾である。キャッシュ最適化、重複整理、区画再配置を理由に前方へ移動・削除・別区画へ分散してはならない。内容を変更する場合は、その変更自体を明示目的として扱い、対応する回帰テストも同時更新する。
9. 深度3・4のdraftへ公開イベントの生オブジェクトを渡さない。公開履歴は通常プロンプトと同じ公開履歴ポリシーから生成した射影を正本とし、`opportunityContext`等の進行管理情報、空値・空配列・空オブジェクト、判断に不要な内部管理項目を工程プロンプトへ掲載しない。draftの構造データは意味を変えずcompact JSONで渡す。
10. 工程プロンプトへ内部UUIDを直接掲載しない。playerは表示名、公開eventは公開イベント番号へ変換し、オブジェクトの値だけでなくキーも境界検査する。雪女の能力対象など、機械契約が内部IDの返却を明示的に要求する箇所だけを例外とし、例外範囲を一般化してはならない。
11. 公開発言ルールの文章整理は否定形を文単位で減らすことを目的にしない。同じ趣旨を複数箇所へ重複させず、優先事項・重複禁止・新規性要求・例外・情報境界の関係が一読で分かる文章全体へまとめる。新規性のための根拠薄弱な疑い・評価変更、実質同じ発言や単なる言い換え、根拠としての発言番号列挙など、実際の誤挙動を止める禁止は否定形のまま明確に残す。文言整理で深度1の意味契約を変更せず、深度2～4も同じ意味契約を維持する。
12. AI応答JSONの`rationale`は結果判明前の具体的な選択理由を原則1～2文、雪女の推定を伴う場合は1～3文とする。パーサー後の内部保存名`selectionRationale`とは責務を分け、AIへ提示するJSON例・Schema・修復契約へ内部名を露出させない。これは前方の出力契約・工程指示で統一し、`最終確認`以下を長さ指針統一のために書き換えない。
13. AI応答JSONの外部キーは`app/renderer/js/prompts/response/responseContract.js`を唯一の正本とする。`responseParser.js`が外部キーを内部保存表現へ変換することは許容するが、内部名を外部契約へ逆流させない。AI応答JSONは製品ユーザーデータのschemaMigration対象ではない。保存済み`rawResponse`は監査用の不透明文字列として扱い、ゲームJSON再読込時に現行AI応答パーサーへ再投入しない。

## 現行ディレクトリ構成と責務

プロジェクト直下には、利用者向けの起動・配布操作ファイルだけを置く。

- `app/package.json`: 製品名、版番号、Electron Mainエントリーの正本。
- `app/main/`: Electron Mainプロセス。ウィンドウ生成、IPC、暗号化設定保存、ゲーム自動保存、独立自由会話保存、独立人狼観戦保存、AIプロファイル別使用量集計、外部AI API、ローカルLLM通信を担当する。
- `app/renderer/index.html`と`app/renderer/css/`: Rendererの画面構造と表示。通常アプリ全体は`styles.css`、公開表示と単体公開HTMLで共有する公開表示スタイルは`publicView.css`を唯一の正本とし、同じ公開表示セレクタを両ファイルへ重複定義しない。
- `app/renderer/js/`: ゲーム状態、ルール、自由会話状態、人狼観戦状態、プロンプト、解析、検証、自動実行、UIの本番ES Modules。

- Windows配布版は`配布版を作成.cmd`または`tools`配下の`npm run release`から生成し、成果物を`output/dist`以外へ出力しない。

- アプリversionはSemantic Versioningの`MAJOR.MINOR.PATCH`を正本とする。不具合修正・既存仕様どおりの挙動へ戻す修正・互換契約を変えない内部改善は`PATCH`、既存利用を壊さない新機能・新役職・設定追加は`MINOR`、既存の利用方法・公開契約・製品仕様を非互換に変更する場合は`MAJOR`を更新する。同一リリースで複数区分に該当する場合は最も大きい区分を採用し、`app/package.json`と`tools/package.json`を必ず同じ値へ更新する。`schemaVersion`と`PROMPT_SPEC_VERSION`はそれぞれ独立した更新規則に従い、アプリversion更新だけを理由に変更しない。

### テスト作成ルール

- テストは製品の意味契約、データ構造、状態遷移、可視性境界、許可／拒否条件、パーサー・validatorの結果、代表的な実行経路を検証する。自然言語の言い回しそのものを仕様として固定しない。
- AIプロンプト、ガイダンス、役職説明、推理方針などの自然文について、`assert.match`、`assert.doesNotMatch`、`includes`、全文snapshot、固定文字列比較などで特定の日本語句・語順・説明文の存在／不在を合格条件にしてはならない。意味を保った短縮・統合・言い換えだけでテスト変更が必要になる状態を作らない。
- プロンプト関連テストでは、入力ポリシー、選択された契約キー、Schema、許可値、公開／私有情報の投影、動的対象、生成された構造データ、解析結果、validatorの受理／拒否、保存結果を直接検証する。自然文に埋め込まれた仕様を確認したい場合は、可能な限りその仕様の正本となる構造データまたはポリシー関数を検証対象にする。
- 「この文言が存在すること」を守るためだけの回帰テストを追加しない。同じ意味を別表現で実現できる要件は文言固定テストの対象外とする。法的表示、外部プロトコル上の固定token、ファイル形式のmagic valueなど、文字列自体が公開契約である場合だけ例外とし、なぜ文字列固定が必要かをテスト内コメントで明記する。
- テストを通す目的でAI向けプロンプトへ説明文、注意書き、重複ルールを追加しない。プロンプト追加は実際のAI挙動または正式仕様上必要な場合だけ行い、同じ責務の既存文を優先して短縮・統合する。
- プロンプト全文snapshotや大量の部分一致で文章構成を凍結しない。セクションの有無自体が意味契約である場合も、可能ならセクション生成条件・構造化入力・組み立てポリシーを検証し、見出し文言や説明本文を固定しない。
- 不具合修正の回帰テストは、その不具合を生んだ意味上の境界または失敗条件を最小入力で再現し、修正後の受理／拒否・状態変化を検証する。過去の回答文や旧プロンプト文言をそのままfixture化して恒久固定しない。
- 既存テストを変更・追加するときは、同じ仕様を別テストが既に守っていないか確認し、重複する文言検査・同値検査を増やさない。テスト数ではなく、独立した製品契約をどれだけ直接検証しているかを基準にする。
- ソースコードの後方互換は不要であり、廃止した旧実装や旧API分岐を残さない。ただし製品版1.0.0以降のデータMigrationとそのfixtureはこの削除規則の明示的な例外とする。

## 公開発言本文の境界

公開発言本文は不透明な文字列として保存・表示する。空文字、既存文字数上限、JSON型、固定形式`#N`による公開発言参照を除き、人物、質問、疑い、CO、能力結果、投票意思、秘密らしさ、言葉遣い、ゲーム上の意味を抽出・推定・照合しない。COは明示的な`coOperation`だけを正本とし、`coOperation.roleId`は本人の真役職ではなく公開上の役職主張を記録する。戦術的な真CO・偽CO・変更・撤回を同じ構造で扱う。

人間の通常公開発言経路が受け取る構造化項目は、`playerId`、公開発言本文、任意CO、任意の個人質問先だけとする。質問先は`questionTargetId`で明示し、自然文から推定しない。AI用の能力結果主張、判断状態、心の声、内部メモ、進行指定を通常発言の人間入力へ流用しない。

人間の回答優先発言は通常発言と別経路とし、公開回答本文、任意CO、任意の構造化能力結果だけを受け取る。通常発言数・巡・発言順を消費せず、質問元はシステムが固定し、新しい質問先を指定させない。

## 人狼非依存チャットルームの責務境界

- チャットルームは人狼ゲームの特殊フェーズではない。`game` State、`discussionRuntime`、ゲームrevision、Undo／Redo、役職・陣営・CO・投票・能力・判断状態・陣営戦略へ混在させない。状態正本は`app/renderer/js/domain/chat/`、Prompt正本は`app/renderer/js/prompts/chat/chatRoomPrompt.js`、会話きっかけ選択正本は`app/renderer/js/prompts/chat/chatRoomConversationCuePolicy.js`、Main保存正本は`app/main/chatRoomStore.js`とする。
- 最新チャットセッションは`chat-room-session.json`へ保存し、`game-autosave.json`へ混在させない。schemaVersionは共通dataCompatibilityを正本とし、製品版1.0.0の基準は1。旧schemaは共通Migration後に現行チャットvalidatorへ渡し、セッション内メッセージは最大1200件とする。
- チャット参加者は有効なキャラクターデータから2人以上を選び、チャット専用の`participants[].profileId`でAIプロファイルを割り当てる。チャットの個別割り当て・一括適用は人狼側`desktop-settings.json`の`assignments`を書き換えない。
- 発言順は通常巡回と優先ターンを分離する。固定または巡回ごとのランダム通常巡回は1巡内で原則1キャラクター1回を維持する。`questionTargetIds`は返答を求める明示的な質問先だけを受理し、質問優先ONのAI質問とプレイヤーの特定キャラ指定は質問メッセージ1件・対象1人ごとに`kind: "answer"`の専用回答ターンを追加する。回答ターンは通常巡回枠を消費せず、同一巡内の同一キャラクター複数発言を許容する。質問優先OFFのAI質問は未解決質問だけ保持する。「次に話す」は`kind: "manual"`として通常巡回枠を移動し、質問回答とは別契約にする。
- 初回会話きっかけは、お題ありでは選択せず、お題なしではキャラクター固有`conversationSeeds`85%／システム汎用cue15%で最初の通常発言者へ1件選ぶ。最初のAI発言以後は通常巡回ターンだけ、きっかけなし85%／固有10%／汎用5%で任意cueを弱く提示する。回答ターンと手動指定ターンへcueを混ぜず、直近利用cueを避ける短期履歴を保持する。汎用cueは10種類を`chatRoomConversationCuePolicy.js`で一元管理し、同じ状態の再生成で選択が変わらない決定的方式とする。
- プレイヤー名はチャットセッション設定で最大80文字として保持し、人間発言の`speakerName`に使用する。プレイヤー専用プロフィールやキャラクターカードを作らず、現行PromptのAI参加者一覧にもプレイヤーを独立参加者として追加しない。AIが認識するプレイヤー情報は会話履歴に現れた名前・発言・指名内容を正本とする。
- AIへ渡す生の会話履歴は直近48メッセージとする。未回答質問は発言者本人宛てのものを別枠で最大8件渡し、質問専用回答ターンではそのターンの元質問1件だけを必須回答として渡す。履歴上限を増やす代わりに他者の私有情報を混入させてはならない。
- キャラクター個別内部メモは共有記憶にしない。`characterMemories[characterId]`へ完成版を置換保存し、次回も本人にだけ再投入する。最大24項目、1項目200文字、総3200文字とし、他キャラクターへ開示しない。AI応答で`memory`が利用可能なら完成版を正本とし、解析時に`memory`配列を得られない場合は既存メモを保持する。
- チャット応答契約は`chatMessage`、`memory`、`interaction.questionTargetIds`、`interaction.answersMessageIds`を使用する。`questionTargetIds`は現在参加中の他キャラクターへの明示質問だけ、`answersMessageIds`は本人宛て未回答メッセージだけを受理する。質問専用回答ターンでは指定元質問IDが`answersMessageIds`へ含まれることを必須検証する。通常Promptは質問や話題展開を弱く許可するが、毎回の質問や機械的な聞き返しを要求しない。人狼用の応答契約や`discussionBehavior`・`reasoningProfile`を流用しない。
- 会話中の参加者差し替えは会話履歴・お題・プレイヤー名を維持する。継続参加キャラクターの内部メモと有効な未解決質問回答ターンを保持し、退出キャラクターの内部メモ・退出者宛て未回答質問・孤立優先ターンを削除する。参加者構成または並びが変わった場合だけ通常巡回キューを再構成し、AIプロファイルだけの変更では通常巡回・優先ターンをリセットしない。
- チャットAPI要求も通常の`desktop:generate`経路とAIプロファイルを使用する。API使用量・料金の集計正本は`profileId`であり、チャットセッションIDを料金集計軸にしない。人狼・チャット・診断など用途を問わず同じプロファイルの累計へ加算し、`profileBudgetUsd`もそのプロファイル全体の累計へ適用する。
- 詳細仕様は`docs/CHAT_ROOM_SPEC.md`を参照し、コード変更時は同文書とユーザー向け`app/README.txt`の一致も確認する。

- 人狼観戦はゲームStateを複製・巻き戻す機能ではない。観戦セッションの状態正本は`app/renderer/js/domain/spectator/`、Main保存正本は`app/main/spectatorRoomStore.js`、公開盤面の時点再生正本は`app/renderer/js/public/publicReplaySnapshot.js`とし、観戦再生位置をゲームrevision・Undo／Redo・`discussionRuntime`へ混在させない。

- 観戦開始時のログ番号は1以上の整数とし、指定番号以上で最初に存在する公開ログから追っかけを開始する。指定番号が最新公開ログより後なら最初からリアルタイムとする。指定した開始ログ以前の履歴は盤面復元にだけ使用し、チャットへ再掲したりAIへ個別ログとして再投入したりしない。
- 追っかけ中の「人狼卓を1手進める」は次の既存公開ログを1件だけ再生し、実ゲームStateを変更しない。リアルタイム中の同じ操作だけがAI管理Controllerの`runSingleAutomaticStep`へ委譲し、人狼進行規則を観戦Controllerへ複製しない。実行ロック、人間入力待ち、手動AI待ち、夜間プライバシーはAI管理側の既存契約を正本とする。
- 追っかけ中の「リアルタイムへ移動」は未再生ログへの観戦AIコメントを生成せず、再生カーソルと全観戦者の既読カーソルを現在の最新公開ログへ移し、最新公開盤面へ合流する。リアルタイム中は同じ位置の操作を「公開表示を再同期」として扱う。

- 推理観戦のAIへは再生位置より後の公開イベント・最新盤面・残件数など未来を推測できる情報を渡さない。神視点観戦は真役職を開始時から参照できるが、生死や座敷わらしの遅延所属など動的状態は再生位置までに成立した情報だけを用いる。
- 「観戦コメントを自動生成」は表示済みの新しい公開ログへのAI反応だけを自動生成する設定であり、追っかけ再生カーソルを進める権限を持たない。ログ送りは常に利用者の明示操作とする。
- 詳細仕様は`docs/SPECTATOR_ROOM_SPEC.md`を参照し、コード変更時は同文書、`docs/tests/人狼観戦通しテスト手順.md`、ユーザー向け`app/README.txt`の一致も確認する。

## 終盤の陣営戦術

生存人数が`2 × (初期配役の人狼枠 + 狂人枠)`以下を終盤判定とする。昼の通常発言・回答優先発言では共通の終盤戦術を提示し、投票では狂人枠にだけ終盤投票の追加判断を提示する。閾値は生存中の真役職ではなく公開済みの初期配役属性から算出し、秘密の生存内訳を判定へ使用しない。人狼枠は`countsAsWolf`、狂人枠は`roleClass === 'madman'`を正本とするため、白狼は人狼枠、雪女は狂人枠となる。遅延所属の座敷わらしは固定閾値へ含めず、本人の所属確定後の戦術分類では既存`strategyProfile`に従い、人狼陣営なら狂人枠として扱う。

終盤では潜伏だけを固定戦術とせず、自分についての真CO・偽CO・変更・撤回・票合わせを勝率で比較できる。村人陣営もPP・RPP回避のための偽人狼COを選択できる。これらのCOは`coOperation`へ公開上の主張として記録し、他者の未公開情報を公開してはならない。投票フェーズでは新しいCOを行わないが、狂人枠は公開済みの騙り結果や前回投票予定との整合性より陣営勝率を優先し、必要なら従来主張と矛盾する投票も比較する。

## 私有情報の境界

心の声、内部継続メモ、判断状態、陣営戦略、本人限定能力情報は保存・GM監査経路を維持し、公開イベントへ格納しない。他AIへは正規の可視権限がある情報だけを渡す。人狼共有戦略などの秘密会話は正規参加者だけが参照する。**heartVoiceの機能・状態・履歴・保存・GM監査表示は絶対に削除しない。** AI生成対象は昼議論（通常発言・回答優先発言）に限定し、応答検証で任意扱いにしても昼議論の生成プロンプトとJSON例から除外しない。
